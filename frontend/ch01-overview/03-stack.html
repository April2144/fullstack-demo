技术栈选型

总览 请求流程 前后端职责 技术栈 环境搭建 项目结构

一、本专题的技术栈

三个模块各选一样，全套只用这四样东西，不加别的。

模块 职责 本专题选型
前端 页面展示与用户交互 HTML / CSS / JavaScript
后端 业务逻辑与接口 Python + FastAPI
数据库 数据存储与管理 MySQL

二、前端：为什么不选框架

方案 特点 适合场景
原生 HTML/CSS/JS 无框架依赖，浏览器直接运行，不需要构建 内容站、CMS、后台管理
React 组件化，生态庞大 大型 SPA、复杂交互
Vue 上手简单，渐进式 中小型项目、快速开发

选原生的四条理由：无构建步骤（不需要 Vite / Webpack）； 学习路径清晰（先掌握 Web 基础，再学框架）；完全可控（每个标签每行逻辑都看得见）； 部署简单（静态文件直接放服务器）。

什么时候该换框架：需要复杂单页应用交互、需要大量现成 UI 组件、 多人协作需要统一组件规范、需要路由/状态管理等完整方案。本专题面向个人站与 CMS，不在这个范围。

三、后端：为什么是 FastAPI

语言 代表框架 特点
JavaScript Node.js / Express 前后端同语言
Python Flask / Django / FastAPI 语法清晰，生态成熟
Java Spring Boot 企业级，稳定
Go Gin 高并发，性能好
框架 特点 适合场景
Flask 轻量，灵活 小型项目、快速原型
Django 全功能，自带 ORM 和 Admin 中大型项目、内容站
FastAPI 异步，类型安全，自动生成文档 API 服务、现代项目

FastAPI 的取舍：自动生成 Swagger UI 与 ReDoc、Pydantic 自动校验、 原生 async/await、代码量少。代价是生态不如 Django 成熟、没有自带后台管理、 ORM 与迁移工具要另外选。

四、数据库：为什么是 MySQL

数据库 特点 适合场景
MySQL 成熟稳定，资料多 大多数 Web 项目
PostgreSQL 功能强大，支持复杂查询 数据复杂、需要高级功能
SQLite 轻量，单文件 小型项目、本地存储

选 MySQL 是因为成熟稳定、资料丰富、适合中小型项目， 并且云服务器上装起来最省事。SQLite 虽然零配置，但不适合多用户并发的线上服务。
