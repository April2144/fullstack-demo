项目目录结构设计

一、为什么前端也要分层

页面少的时候随便放都能跑。页面一多，问题就来了：改一个按钮样式，要在十几个 html 里找； 接口地址变了，要全仓库搜索替换。

分层的唯一目的：能一眼看出某个文件属于哪一层，改需求时知道该改哪、不该改哪。

二、推荐目录结构

frontend/
├── index.html              # 入口页
├── pages/                  # 页面层：只组装，不写业务细节
│   ├── home.html
│   ├── list.html
│   └── detail.html
├── components/             # 组件层：可复用的小块
│   ├── header.html
│   ├── card.html
│   └── pager.html
├── js/
│   ├── api/                # 接口层：所有请求集中在这里
│   │   ├── request.js      # 统一封装 fetch
│   │   └── notes.js        # 具体业务接口
│   ├── pages/              # 页面逻辑：一个页面对应一个文件
│   │   ├── home.js
│   │   └── list.js
│   └── utils/              # 工具层：纯函数，不依赖 DOM
│       ├── format.js
│       └── dom.js
├── css/
│   ├── base.css            # 重置 + 变量
│   ├── components.css      # 组件样式
│   └── pages.css           # 页面专属样式
└── assets/                 # 图片、字体等静态资源
    ├── img/
    └── fonts/

三、四层职责与依赖方向

依赖只能从上往下，不能反向 —— 这是分层能不能立住的关键。

pages → components → api → utils
层 只做 绝不做
pages 组装组件、绑定本页事件、调 api 写通用工具函数、拼 SQL 式的请求细节
components 渲染一小块 UI、暴露参数 直接发请求、依赖某个具体页面
api 拼 URL、发送请求、统一错误处理 操作 DOM、弹提示框
utils 纯函数：格式化、校验、转换 发请求、读写 localStorage

为什么 utils 不能发请求？因为一旦它发请求，就再也测不了 —— 纯函数给输入就该出输出，不依赖网络。

四、就近原则：什么时候不该分层

只有一处用到的东西，不要提前抽成"通用模块"。

该抽出去

  • 三个页面都在用的日期格式化
  • 每个请求都要带的 token 头
  • 反复出现的卡片结构

不该抽出去

  • 只在一个页面用一次的格式化逻辑
  • 只有两个字段的"工具类"
  • 为了"看起来专业"而建的抽象层

判断标准：能说出第二个使用场景，才值得抽。说不出来就先放在用它的地方。
